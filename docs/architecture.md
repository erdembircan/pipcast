# Architecture

Pipcast is three programs that never call each other. Each Claude Code session runs the **mod**. One **station** process owns the window. The **broadcast** runs inside the station's web view. They meet in one folder of files, the **store**.

```text
 Claude Code session ─┐                                   ┌─ station (pipcast-station serve)
   the mod            │   ~/Library/Application Support/  │    the window, its controls, sound
   band, /pipcast,    ├──▶   Pipcast/sessions/<id>.json ───┤    ├─ reads the store every second
   events → record    │      control.json  station.json   │    └─ web view: the broadcast
 Claude Code session ─┘      prefs.json  options.json      │         director → scenes → KLWD graphics
   (any number on air)                                     └─ quits when nothing is on air
```

Every part is built from small pieces with no side effects of their own, so each can be tested alone: the mod's record reducer and band artwork, the station's geometry and store reading, the director's schedule. The side effects sit at the edges: the mod's file and process calls, the station's window, the web view's bridge.

## The store

One folder, `~/Library/Application Support/Pipcast`, created with mode 0700. `PIPCAST_HOME` moves it, for tests.

| File | Written by | What it holds |
| --- | --- | --- |
| `sessions/<session id>.json` | That session's mod | Its `SessionRecord` while it is tuned in |
| `station.json` | The station | `{ v, pid, startedAt, heartbeatAt, version }`, rewritten every 5 s |
| `control.json` | The station | `{ v, closedAt }`: when the window's close button was pressed |
| `prefs.json` | The station | `{ v, sound, quadrant, scale, lastReportAt }` |
| `options.json` | The mods | `{ v, transparent }`: Transparent window, for the station (Telling the station, below) |
| `station.lock` | The station | Held with `flock` for as long as a station serves, so there is only ever one |
| `station.log` | The station | One line per event worth knowing, for debugging; cut back at 1 MB |
| `dev/` | `scripts/cue.mjs` | Development only: cues for the live checkout's development build, whose station takes each one and deletes it (The development build, below) |

A file is written whole to a temporary name beside it, `<name>.tmp`, or `options.json.<session id>.tmp` for the one file any session may write, and renamed into place, so a reader sees the old version or the new one, never half of one. A reader that still meets a file it cannot parse skips it until the next read.

A session deletes its record when it tunes out or ends. One that stops without ending, as when Claude Code is force-quit, leaves its record behind, and the station shows it no more once its check-ins stop. The next session to tune in deletes every record, and every temporary file beside one, that no session has written for an hour (`ORPHAN_MS`). A session that is still running writes its whole record every 10 s, so only a Mac asleep for longer keeps one quiet that long, and it writes its record again at its first heartbeat after the Mac wakes.

### The session record

```ts
type SessionState = 'working' | 'needs-input' | 'ready' | 'error'
type StoryKind = 'needs-input' | 'ready' | 'complete' | 'error'

interface Story {
  id: string          // `${sessionId}:${seq}`, unique for the session
  kind: StoryKind
  at: number          // ms since the epoch, when it landed
  command?: string    // needs-input, a permission: the command, or "Edit src/a.ts"
  quote?: string      // the description, the question, the last words, or the error in words
  added?: number      // ready: lines added since the session's last finished story
  removed?: number    // ready: lines removed since then
  files?: number      // ready: files changed since then
  durationMs?: number // ready, complete, error: how long the turn ran
}

interface SessionRecord {
  v: 1
  id: string           // the session's id
  title: string        // the session's title as it is written
  project: string      // the repository's name, else the folder's
  state: SessionState
  stateAt: number      // when the state last changed
  tunedInAt: number    // when it tuned in: the order on air
  checkedInAt: number  // the mod's heartbeat, every 10 s
  stories: Story[]     // the newest 10, oldest first
  activity: { at: number; text: string }[]  // the newest 3 tool lines, oldest first
  hours: { hour: string; added: number; removed: number; files: number }[]  // the newest 3, keyed "YYYY-MM-DDTHH" in local time
  limits?: { kind: 'session' | 'week'; percentUsed: number; resetsAt: number | null; at: number }[]  // the account's usage limits as this session last read them
}
```

- A record is **live** while `now - checkedInAt` is 45 s or less. A session that stops checking in, because it crashed or the Mac slept, leaves the board.
- **On air** are the live records sorted by `tunedInAt`, then by `id`: all of them, with no limit. Every mod and the station apply this same rule, so they agree on who is on air without talking.
- `control.json`'s `closedAt` tells every mod that tuned in before that moment to tune out: the window's close took every session off the air.

## The mod

The mod's sources are in `packages/mod`: one hooks module, `src/register.tsx`, which only wires hooks to the code in `src/core`, and the plugin's manifest, `plugin.json`. The build bundles them into `plugin/hooks/register.js`, the hooks module an install runs (What ships, below).

- `packages/contract` holds the types, constants and words that the mod, the station and the broadcast share.
- `src/core` holds the mod's logic with no `$` in it: the record reducer, the descriptions of tools and permissions, the diff counter and the ledger that reads git for the lines changed, the band's artwork, what a session's start says about it, the options `/pipcast` sets and how they are saved, and the services that tune in, tune out and check in. The services and the ledger talk to the world through an `Io` port: read, write, list and rename files, look up a file's size and when it last changed, run a command with a time limit, read the clock.
- `register.tsx` builds that port from `$` and hands it to the services. Only functions at the top of that file take `$`, which is what `claude plugin validate` asks for. `register` itself is declared as a function, so it stays one in the bundle, where the validator looks for it.

What it listens to:

| Event | What changes |
| --- | --- |
| `turn.start` | The session is working. Its own tree is read afresh, so what you changed between turns does not count as its work |
| `tool.call` | One activity line. `AskUserQuestion` is a needs-input story with the question; when the call returns, the session is working again. When a call that can change files returns, the main loop's or a subagent's, the tree it ran in is read again and what changed is booked (Lines changed, below) |
| `classic.PermissionRequest` | A needs-input story with the command and Claude's description of it |
| `classic.Stop` | While work the session started will wake it again, still working, with no story yet: a command left running in the background that works (Background commands, below), a subagent, a workflow, an MCP task or an MCP server's monitor, or a scheduled wake-up. Otherwise a ready story when files changed since the session's last finished story, with the lines, or a complete story with Claude's last words |
| `classic.StopFailure` | An error story, its kind in plain words |
| `turn.complete` | For a turn no `Stop` or `StopFailure` ended: an API error is an error story; an interrupt, or any other end, leaves the session ready, with no story |
| `classic.SessionStart`, `classic.UserPromptSubmit` | The session's title, when they carry one. A `SessionStart` that starts a new session, while **Tune in every new session** is on, sets it to tune in by itself (Tuning in by itself, below) |
| `session.attach` | The desktop app shows the session: one waiting to tune in by itself tunes in |
| `session.measure` | The account's usage limits, after each reply and whenever one moves a whole point: each limit it reports replaces the record's of its kind, and the record is written at once when a figure moved |
| `session.end` | The record is removed: the row leaves the board |

The mod keeps its record in memory whether or not the session is tuned in, so tuning in mid-turn shows the right state at once. It writes the record only while tuned in: at once for a new state or story, at most every 2 s for activity, and every 10 s as a heartbeat. The heartbeat also reads `control.json`, starts the station again if `station.json` has gone quiet for 20 s, and looks again at the background commands a finished turn waits on (Background commands, below).

The title on air is the one the engine keeps. The engine writes a session's title to a small file beside its transcript, `<the transcript's folder>/<session id>/custom-title.json`, the moment it changes: a rename in the desktop app or with `/rename`, or a title the app gives the session itself. While the session is tuned in, the mod reads that file once a minute, a read of a few dozen bytes that starts no process, and writes the record at once when the title has changed. Tuning in reads it first, so the record carries the current title from its first write. With no file, or no title in it, the title is the latest one a hook carried, else the default name; a file caught half-written leaves the title as it was. Every classic hook says where the transcript is; after a reload, before one has fired, the mod finds the transcript once with `find`.

The usage limits are the account's, not the session's. Claude Code reports them to a mod after each reply, and the mod reads them again as the session tunes in and after a reload. The record keeps the newest reading of each limit the session took, the five-hour window as `session` and the seven-day window as `week`, with the time it took it; a gateway's spend limit is left out. Claude Code stops reporting a window once its reset time has passed, so the record keeps it until a new one comes. A session with no reply yet, or an account with no plan, has none.

### Lines changed

The lines on air are counted where the work happens, as it happens. The mod keeps a reading of each git working tree the session's work runs in: the session's own folder, and the worktree of each subagent, which the engine names in its note on the subagent beside the transcript (`<session id>/subagents/agent-<agent id>.meta.json`). A tree is first read just before the first call that can change files there. The calls that can are Bash, Edit, MultiEdit, Write and NotebookEdit, from the main loop or a subagent. After each one the tree is read again, unless the engine ran the call read-only, and what changed since the last reading is booked at once in two places. One is the hour it happened in, which the report on the hour adds up. The other is the tally for the session's next ready story. A turn that ends with work still running leaves its tally to the next turn.

A reading is the commit (`git rev-parse HEAD`), each tracked file's lines against that commit (`git diff-index -M --numstat`), and the untracked files (`git ls-files --others --exclude-standard`), each counted as all its lines added. So a new file counts once, whether it is later added, committed or both. When the commit has moved since the last reading, through a commit, a pull, a rebase or a checkout, nothing is booked and the next reading starts from the new commit. The session's own lines were booked as they were written, and lines that arrive from elsewhere are not its work. The one thing this misses is a single command that both changes files and commits them. Each turn also starts with a fresh reading of the session's own tree, so what you change between turns is not counted, and ends with one more, which catches what no call's reading did. Outside git, the edit tools' own figures count once a call has run.

The readings live in the mod's memory. A reload starts them over and keeps the record's stories and hours. The session's next story is numbered after the newest one the record holds, since the station takes a number it has already seen for a story that has aired.

### Background commands

A session stays working after a turn while a command it left running in the background works: the engine wakes the session when that command ends, and the session carries on. A command that runs until it is stopped never ends by itself, so the session does not wait on it. A session that keeps a dev server or a watcher up while it works on a pull request still finishes its turns, and each one's story lands as the turn ends.

A Stop names each background command by its task id and the line it runs, and nothing more. The mod tells what each command is doing from three things, cheapest first:

- **What it runs.** A line that runs a program that never ends by itself: `tail -f`, `docker compose up` unless detached, a program that runs a command on every change, such as `nodemon` or `watchexec`, or a build tool, test runner or runtime in watch mode, such as `tsc --watch`, `vite build --watch` or `npm run watch`. Never a bare flag: `gh pr checks --watch` ends when the checks do.
- **Whether it serves.** The engine runs each background command in a shell of its own, which leads its own process group and writes the command's output, and that of everything it starts, to a file named after the task, `<task id>.output`. One `ps` and one `lsof` find each command's processes from that file: the ones writing to it, the rest of the group the shell leads, and what they started. A second `lsof` asks whether any of them listens on a TCP port: a dev server, a database, a tunnel.
- **What it says.** The first and last 4 KB of its output, for a program saying it waits for files to change: `Watching for file changes.`, `waiting for changes`, `[nodemon] watching path(s)`.

A command none of these settle works, and so does one whose processes cannot be found: a Monitor's output goes to the engine rather than to its file, and a Monitor ends by its deadline. A look that cannot be made counts every command as working, as the mod counted them all before. No look runs while a subagent, a workflow, an MCP task or a scheduled wake-up holds the session anyway.

A server that starts listening a few seconds after the turn ends, or a watcher that says so after its first build, is still working at the first look. So while a turn's story waits on background commands alone, the heartbeat looks again: at every beat for two minutes after the turn ended, then about once a minute. Once none of them works, the story lands, with the lines the turn changed and how long the turn ran. A turn that starts first, because a command ended and woke the session or because you wrote to it, drops the waiting story and ends with one of its own. A look takes about 150 ms.

### The options

Pipcast has two options of its own, each a boolean `userConfig` field in the plugin's manifest, with a word of its own after `/pipcast`: **Tune in every new session** (`autoTuneIn`, `/pipcast auto`), on by default, and **Transparent window** (`transparentWindow`, `/pipcast transparency`), off by default. Claude Code keeps them with every plugin's options in `~/.claude/settings.json`, under `pluginConfigs` and the plugin's id (`pipcast@erdembircan-plugins` for a copy from that marketplace, `pipcast@pipcast` for an install from this repository's own marketplace, `pipcast@synced` for a copy a terminal session synced from Anthropic's plugin directory, each with options of its own), shows them in its plugin options (`claude plugin configure <plugin id>`), and hands them to the hooks module as the second argument of `register`. Until an option is saved, `register` gets the manifest's default for it, and `claude plugin configure --json` reports that default, so `/pipcast auto` says on. Every session watches those settings: a change reloads Pipcast in each of them with the new values, and a new session reads them as it starts.

`/pipcast <option> on` and `/pipcast <option> off` change one from any session, `/pipcast <option>` reads it, and `/pipcast` on its own still tunes the session in or out. The desktop app's plugin page shows no options for a plugin that Claude Code installed, so this is the way to change them in the desktop app. The mod saves an option with Claude Code's own `claude plugin configure --values-stdin`, the command the desktop app's own plugin settings run, on the engine the session runs on: `CLAUDE_CODE_EXECPATH` when it is set, else the parent of a command the mod starts, which is the engine itself. The plugin's id is the entry in `claude plugin list --json` that is read from, or installed at, the mod's own folder. A copy Claude Code did not install, one loaded with `--plugin-dir` or handed to the session by the desktop app, keeps its options as `pipcast@inline` and is reached with `--plugin-dir`.

### Tuning in by itself

While **Tune in every new session** is on, a new session tunes in by itself, once, as soon as it is both new and on the desktop:

- **New** is what `classic.SessionStart` says: a session that starts fresh, the one a `/clear` starts, or a fork. A resume carries on an old session, which is left as it is, and a compaction changes nothing.
- **On the desktop** is the desktop app showing it: `session.attach` with the `desktop` surface, or `desktop` already among `$.session.surfaces()` when the session starts, as after a `/clear`. A headless run, `claude -p` from a shell or a script, is shown nowhere, so it never tunes itself in, and nor does a session shown only in VS Code or on a phone over Remote Control.

A new session the desktop app has not shown yet waits until it does. The wait is kept in the session's `$.state` as `due`, so a reload does not lose it.

It is the same tune-in as **TUNE IN**: the record, the station, the plate turning to **TUNE OUT**, and the toast when the station cannot start. It happens once. Pressing the plate or running `/pipcast` first settles it, and so does the tune-in itself: a session you tune out stays off the air when the desktop app shows it again. A reload starts no session, so it never tunes one in, and turning the setting on changes only the sessions that start after it.

### Telling the station

The station follows **Transparent window**, and it reads only the store, so the mods write the option where it looks: `options.json`, `{ v, transparent }`. `/pipcast transparency on` and `off` write it as soon as Claude Code has saved the change, whether or not the session is on air. A session that tunes in writes its own value before the station starts, and so does one that reloads while tuned in, when the file is missing, cannot be read or says otherwise; that is how a change made in a terminal's `/plugin` reaches the window. Every session reloads with the new value after a change, so they all write the same one. A session whose reload has not come through yet writes its old value if it tunes in meanwhile, and its reload puts the new one back. Any session may write the file, so each writes it through a temporary file named after itself, and two writing at once never move each other's.

### The band

Desktop only, and never while a survey holds it. The band is one line of its own: what another mod drew stays as it was, on its own line above ours, and with no other mod there the plate is the band's only line, centred in it. It draws one picture and no words of its own: a plate with KLWD in chrome and, at its end, TUNE IN or TUNE OUT. It shows no count, so it is the same however many sessions are on air. A mod's button shows only text, so the plate is an `Svg` with a blank, plain `Button` laid over it. The picture is built from outlines of the station's lettering, since an image loads no fonts.

## The station

`station/` is a Swift package. `StationCore` holds everything that can be tested without a window: the geometry, the visibility rule, when the window counts as hovered and how opaque it is, when it is minimized and how it slides into the side and back, reading the store, the preferences, the command line and the lock. `StationSound` holds the sound, and its checks play it in an engine that renders offline. `PipcastStation` is the app.

### One station, started by whoever needs it

`pipcast-station launch` starts a station unless one is serving, and returns at once. The mod runs it when a session tunes in and whenever the heartbeat finds the station gone. It starts `pipcast-station serve` in a session of its own, with no terminal and no parent waiting on it, so the station outlives the session that started it. `serve` takes `station.lock` or exits, which keeps one station however many sessions start one at the same moment.

The station quits by itself: 5 s after nothing is on air, or 20 s after it started if nothing came on air at all, or at once when its close button is pressed. With nothing on air there is no window.

### The window

The proof of concept's recipe: a borderless, non-activating `NSPanel` at the status-bar level (25), on every Space and beside full-screen apps, in an app with the accessory activation policy. It is shown only from `applicationDidFinishLaunching` on, so it never takes the keyboard from the app that started it.

- **When it shows.** While any app but Claude is frontmost. It hides while the Claude desktop app is, and while you are on Claude's full-screen Space, whichever app is frontmost there. It hides at once, with no fade.
- **Claude's full-screen Space.** The window is on every Space but the ones Claude fills alone in full screen, so it never shows over Claude in full screen, not even while you switch to it. A full-screen Space Claude shares with another app in Split View is not its own, and the window shows there as anywhere else.
- **Its size.** Its quarter of the screen's visible area, less 20 pt on every side, at 16:9. You can make it smaller, down to 70%, by dragging one of the two edges that face the middle of the screen, or the corner between them; the outer corner stays put. Over those edges the pointer becomes macOS's window-resize pointer, with a single arrow when the window is as big or as small as it gets. The size is kept as a share of the quarter, so it carries to another screen.
- **Moving it.** Drag it anywhere. On release it goes to the quarter that holds its centre, in 0.2 s.
- **Minimizing it.** On hover a glass handle shows at the middle of the window's inner edge, the one that faces the middle of the screen, pointing to the side the window goes: its own, right for a window in a right quarter and left for one in a left quarter. Pressed, the window slides into that side in 420 ms, and the handle stays at the edge as a tab, the only thing on screen; dragging a quarter of the window past the left or right edge does the same at once, before you let go, unless another display lies beyond that edge. A click on the tab, or a pull toward the middle, brings the window back in 460 ms. The window goes into its own screen's visible edge, the part past the edge cut away as it goes, so it never shows on a display beside it. The station keeps the choice in `prefs.json`, so a station that starts again starts minimized. With Reduce motion on, the window and the tab cross-fade instead. The handle and the tab are one small panel of their own, one level above the window and never attached to it: the station moves it with the window through every drag, resize and snap into a corner. While you drag the window, the handle follows: once the window's centre crosses the middle of the screen, it moves to the window's other edge and points the other way, to the side a drop there would send it.
- **Out for a segment.** While the window is minimized, the station brings it out whenever the page asks for it, which it does only for BREAKING NEWS and the report on the hour, and takes it back the moment the page stops asking. If the pointer is on the window then, it waits until the pointer leaves, so a click meant for the window never lands on the app beneath. A segment only borrows the window: if Claude comes to the front during one, the window is minimized again when it next shows, and pressing the handle during one sends it back at once.
- **Its look.** Corners of 20 pt, a hairline edge, macOS's own shadow.
- **Its controls.** On hover the picture dims a little and three 44 pt glass buttons appear, 8 pt in from the top corners: close at the top left, sound and Back to Claude at the top right. They use macOS's clear Liquid Glass where there is one, and brighten under the pointer. Nothing pops up over them. The minimize handle shows with them.
- **Transparent window.** While **Transparent window** is on, the whole window shows at 40% while the pointer is elsewhere, so what is under it reads through, and turns whole as the pointer reaches it, fading with the controls, 0.15 s in and 0.25 s out. Everything airs the same either way, BREAKING NEWS included, and the window takes clicks and drags as before. The station reads `options.json` as it starts and every second after, and fades to a changed setting at once.
- **Hovered.** The window counts as hovered while the pointer is on it, and while a press that started on it is held, so a drag that carries the pointer off its edge leaves it whole with its controls up. The station asks again from where the pointer is whenever the answer could change: as the pointer enters, leaves or moves over the window, as a press starts and ends, as the window shows, once it settles into a corner after a drag, and every second, since macOS says nothing to a window that appears under a resting pointer or moves out from under one.

### The web view and its bridge

The broadcast is a web page in a `WKWebView` that never receives a mouse event: a transparent view above it takes every click and drag. The two sides speak in JSON messages.

| From | Message | When |
| --- | --- | --- |
| Station | `{ type: 'snapshot', now, visible, windowOut, sessions, lastReportAt }` | When the store changes, when the window shows or hides, when it starts to move into the side or out and when it lands, and every second |
| Page | `{ type: 'ready' }` | Once it is listening for the station's messages |
| Page | `{ type: 'cue', jingle }` | A step starts with a jingle, or a segment ends whose outro was left out; the station plays it at once, unless sound is off |
| Page | `{ type: 'bed', bed }` | The first step with the beat under it starts; the station mixes the beat in and loops it, unless sound is off |
| Page | `{ type: 'bed-out' }` | A step without the beat starts after one with it, or the segment ends; the station phases the beat out |
| Page | `{ type: 'hush' }` | A segment on air is cut; the station fades out everything playing |
| Page | `{ type: 'reported', at }` | The report on the hour starts; the station keeps `at` as `lastReportAt` |
| Page | `{ type: 'window', wanted }` | Whenever the director's answer changes to whether a segment needs the window out: true as one is due, on air, or waiting between two; false in the tick the last outro ends |
| Station | `{ type: 'still', input }` | Snapshot mode: draw this one picture, without motion |
| Page | `{ type: 'rendered' }` | Snapshot mode: the picture is drawn |
| Station | `{ type: 'dev', cue }` | The development build only: a cue, as its file's text (The development build, below) |

`sessions` holds every record on air, as the store has them.

`windowOut` is true while the window is out in its quarter and still, open or out for a segment, and false while it is minimized or moving. A snapshot without it counts as out.

### Sound

The sound is rendered at build time from the design system's scores: the four jingles as AAC, and the beat in its two keys, each as a loop one turn long in Apple Lossless, so the loop comes round to the frame. The station plays them with an `AVAudioEngine`, at the Mac's volume: three players for the jingles, so an outro's ring can run on into the next segment's start, and one for the beat. Sound starts on; the window remembers the choice.

Each message changes what plays as it comes, 40 ms later on the engine's clock, so that everything one event starts starts together. Nothing is timed ahead. The beat mixes in over 300 ms on the last notes of its line, rising evenly from silence, so that its first downbeat lands at full; it loops until the page says it goes, then phases out over 500 ms, falling as the square of what is left, so that it carries into the outro's first chord and is gone before its second. A hush fades everything out over 80 ms. Sound hushes the same way when the page loads again and when you turn it off; turned back on, it plays from the next segment. A beat still playing when no segment needs the window any longer phases out. The three lengths are `BED_IN_MS`, `BED_OUT_MS` and `HUSH_MS` in the contract, and the design system's player mixes with the same.

The engine runs only while it has something to play: it starts with a segment's first sound and pauses a second after the last one has played. A running output costs about 1% of a core even in silence, and macOS keeps the Mac awake while one runs. So a segment's first sound waits for the output to start, as it did with `AVAudioPlayer`: about 80 ms on the Mac's speakers, and up to half a second on Bluetooth headphones. The station starts the engine as the page asks for the window, which for a window minimized to the side is half a second before the open, time enough for either. Once the first sound plays, the engine runs on through the segment, BREAKING NEWS's jingle ringing into the desk and the beat on to the outro, so every sound after it lands on its event. When the Mac's output changes, a device plugged in or out, the engine stops by itself; the station starts it again and plays on what was still playing, the jingles from where they had got to and the beat at its place in the turn.

## The broadcast

`packages/director` decides what airs. `packages/renderer` is the web page that draws it with the KLWD components from `design/`.

The director is a pure function of time and the latest snapshot. Each tick it returns a scene for the design system's `Broadcast` component, a key that changes when a new step begins, and what the station is to play from that tick. The page ticks it every 250 ms and again as each snapshot arrives: the system runs a hidden page's timers late, and the director has to see every snapshot the window was hidden in. A segment is a list of steps, and a step can start with a jingle and have the beat under it. The beat comes in as the first step with it starts, plays on through the steps after it that have it too, and goes as a step without it starts or the segment ends; a segment that is cut hushes everything. So the sound follows the picture's events, and has no lengths of its own:

| Segment | Steps |
| --- | --- |
| A story | BREAKING NEWS 1.9 s, cue `breaking`; the desk 10 s, the beat in D minor under it; the outro 1.4 s, cue `breaking-out` |
| The hour | The ident 7.5 s from five seconds before the hour, cue `hour`; the desk 10 s, the beat in D major under it; THE HOUR IN REVIEW 10 s for each page of four rows, the beat playing on, left out in a quiet hour; the outro 1.6 s, cue `hour-out` |

Between segments, the live board. The rules, from the design system's *Event desks*:

- Stories air one after another, in the order they land, at least 2 s apart. Nothing cuts in. A story that lands during another waits in the ticker as COMING UP.
- A story whose session has moved on is dropped before it airs, and cut short at the desk if it moves on while on air. A story cut short is not restarted.
- The report on the hour joins the queue only if the window shows as the hour strikes: at some moment in the five seconds before the hour, while its ident is due. If the window is hidden all that time, that hour's report is skipped, and showing the window later, tuning a session in or starting the station after the hour never brings it back. Once in the queue, the report waits its turn like a story and keeps its place while the window is hidden; one still waiting when the next report comes due is dropped. The next report covers everything since the last one that aired.
- While the window is hidden, Claude is in front and shows every story itself. Nothing airs: a segment on air when the window hides is cut, the stories waiting their turn are dropped, and a story that lands while it is hidden never joins the queue. Only the report on the hour waits.
- While the window is minimized to the side, a segment waits for it. The page asks the station for the window as soon as a story or the report on the hour is due, the station brings it out, and the open starts as it lands. A segment on air when the window goes back into the side, because you pressed the handle, is cut and not restarted, as when the window hides; what waits keeps its place, and airs in its turn, bringing the window out again. A waiting story whose session moves on is dropped there and then, so it never brings the window out for nothing.
- The listing goes by state: needs input, error, ready, working. Within needs input and error the session waiting longest comes first, counted from its newest story of that kind, as the ticker's STILL WAITING counts it; within ready and working, the one whose state changed last. Sessions that tie keep the order on air. THE HOUR IN REVIEW lists its rows in the same order, taken as the report starts.
- The board shows four sessions a page. With more, the listing turns its own pages every 8 s, on a clock that starts when the board appears, so it always comes back on its first page; what changes while a page is up waits for the next turn. THE HOUR IN REVIEW pages the same way, 10 s a page.
- Under the listing, the board shows the account's usage limits, each from the newest reading of any session on air: a whole percent, rounded as usage-band rounds it, and 0% for a limit past its reset time. They are on the board, under an outro's board too, and nowhere else: not at the desk, not in THE HOUR IN REVIEW.
- With reduced motion, the openers show their last picture, the outros cut straight to the board, and the listing's pages cut instead of turning.

## The development build

The live checkout runs as the development build: what `plugin/` holds, with the station and its page built to take cues, so that `scripts/live.sh story` and `scripts/live.sh hour` air BREAKING NEWS or the report on the next hour now, from the sessions on air or with words and figures of their own. The station takes cues only when it is compiled with `PIPCAST_DEV`, and the page only when it is built from `packages/dev`, an entry of its own. Neither ever goes into `plugin/`: the station and the page that ship have no way in for a cue, and nothing in them knows what one is. CI compiles no Swift, so `scripts/test.sh` compiles the development build of the station too.

- **The build.** `scripts/build-dev.sh` builds it from the checkout it runs in into `.dev/`, which git ignores: the station with `PIPCAST_DEV` in a Swift scratch folder of its own, the page with `scripts/build-web.mjs --dev`, and the two laid into a copy of `plugin/` as `.dev/marketplace/plugin.next`. `scripts/live.sh` runs the live checkout's own copy of it on every move, swaps the result in for `.dev/marketplace/plugin` with two renames, so a station running the build before is never overwritten, and writes the commit it came from to `.dev/marketplace/BUILT-FROM`. The `pipcast` marketplace points at `.dev/marketplace`, so that folder is the one every session reads and the station runs from, whatever the live checkout has checked out. A commit from before the development build has no `scripts/build-dev.sh`, and its `plugin/` goes in as it is. `.dev/` stays out of git at any commit, through the main checkout's `.git/info/exclude`.
- **The way in.** `scripts/live.sh story`, `hour` and `cue` run the live checkout's own `scripts/cue.mjs`, which writes each cue to a file in the store's `dev` folder, through a temporary file. The development build's station looks there every second, hands each file's text to its page as `{ type: 'dev', cue }`, oldest first, and deletes it. It puts `+dev` after its version in `station.json`, which is how `scripts/cue.mjs` tells it from any other station, and it logs each cue it takes and each sound and window the page asks for, so `station.log` says what aired.
- **The cue.** `packages/dev/src/cue.ts` reads one: a story cue with one to eight stories, or an hour cue with the sessions its report covers, when not the ones on air. The page drops a cue it can't read and logs why. `scripts/cue.mjs` runs the same code with Node itself before it writes one, which is why `packages/dev/src` imports with relative paths only.
- **Its turn.** A cue waits until the window shows and the station's own director has nothing on air or due, and then 2 s more, as between any two segments. It waits five minutes at most, from when the page got it, so a cue left behind never airs into a later visit.
- **A director of its own.** A cue airs on a director made for it, which sees the snapshots as they come, so the segment is the director's own, step by step and sound by sound. Meanwhile the station's own director sees every snapshot with the window held to the side, as if minimized: it starts nothing, a story that lands meanwhile joins its queue and airs after the cue, and the hour comes due for it as ever. The cue's director sees only the stories there were when it began, so nothing airs twice. Hiding the window cuts the cue's segment, and it never airs again. With no cue, every tick goes straight to the station's own director, so the development build airs what a release does.
- **Made as it airs.** A cue's stories and sessions are made as its segment starts, so every time in them is fresh: a story stamped when it was cued, then left waiting for the window, would be one the director first sees old, and the director airs no such story. A story lands on a session of its own, in the state the story leaves it in, or on a session on air that it names, which then shows that story alone.
- **The report on the next hour, now.** The cue's director first sees the sessions with the window hidden, so it takes in their stories and airs none. Then it sees the next hour come due at five seconds before it, with the window held to the side, so the report joins its queue and waits. From then on it goes by the clock, and airs the report at once. The ident counts down to that hour as it always does, and the desk and the review show the time it is. The report covers what the sessions did since the last report, as the one at the hour would.
- **Nothing kept.** A cue's director is dropped when its segment ends, and posts no `reported`. `prefs.json` and the station's own director are as they were, so the report at the hour still comes, and covers the whole hour.
- **Which station runs.** Any session on air starts the station when it finds none, from the plugin it runs, and a session that hasn't reloaded since a switch still runs the Pipcast before it. So `scripts/live.sh` doesn't leave it to them. After a move that changed the station, or that turned off the release in Claude Code's plugin list whose station was on air, and on `scripts/live.sh restart` while the live checkout is in the app, it stops the station on air and starts the live checkout's itself, stopping again any station a session starts in between. A move leaves alone a station from a copy the desktop app hands in, which `scripts/live.sh` can't turn off, and says to turn that copy off and run `scripts/live.sh restart`. Every session, whatever it runs, feeds the station there is, as it would any.

## What ships

An install copies `plugin/`, the folder Anthropic's plugin directory and both marketplaces name, as it is. Claude Code has no ignore file or list of files for a plugin, so `plugin/` holds only what runs, and `scripts/build.sh` writes all of it from the sources:

| In `plugin/` | Built from |
| --- | --- |
| `hooks/register.js` | `packages/mod/src` and `packages/contract/src`, bundled into one ES module |
| `hooks/hooks.json` | Written by the build: it names `register.js` |
| `.claude-plugin/plugin.json`, `types/index.d.ts` | `packages/mod/plugin.json` and `packages/mod/types/index.d.ts`, copied |
| `README.md` | `packages/mod/README.md`, copied |
| `assets/icon.png`, `LICENSE` | `assets/icon-1024.png`, rendered on a Mac from the icon `scripts/build-icon.mjs` draws, and `LICENSE`, copied |
| `station/pipcast-station` | `station/`, built on a Mac |
| `station/web` | `packages/renderer`, `packages/director`, `packages/contract`, `design/components` and `assets/fonts`, with React's production files and license copied unchanged from `node_modules` into `station/web/vendor` |
| `station/sounds` | The design system's scores in `design/components/bundle.js`, rendered on a Mac: the jingles as AAC, the beat's two loops as Apple Lossless |

Everything else stays on the development side of that line: the TypeScript sources, the unit tests in each package's `test/`, the kit tests in `packages/mod/kit`, the type configurations, the scripts, the icon's layers in `assets/icon-layers`, the stamps in `scripts/build.d` that say which sources the station binary, the jingles and the icon's PNGs were built from, and the development build, which `scripts/build-dev.sh` builds into `.dev/` (The development build, above).

The bundle is an ES module that imports `claude-code`, with its JSX compiled against the engine's `h` and `Fragment`, and it is never minified: `claude plugin validate` reads a hooks module's source, and it finds the same hooks, calls, environment reads and state keys in the bundle as in the sources. Its paths are relative to the repository, so it builds the same on any machine.

The build doesn't minify the broadcast's page either, since Anthropic's plugin directory holds code it can't read for a reviewer. `station.js` is the page's own code, bundled as written, with its JSX compiled to `React.createElement`. React comes as its own production files, `vendor/react.production.min.js` and `vendor/react-dom.production.min.js`, the same bytes as in its npm package, and `index.html` loads them before `station.js`, which takes `React` and `ReactDOM` from them. Each file stays under the directory's 256 KiB.

Four checks hold the line:

- The build's last step, `scripts/build-plugin.mjs`, stops when `plugin/` holds a file that is not in `SHIPS`, the one list of what an install gets, or lacks one that is.
- `scripts/test.d/40-mod.sh` runs the kit tests against the built plugin rather than the sources. `claude plugin test` loads the plugin from the folder it is given and runs every test under that folder, so the kit and the sources it takes its words from are laid beside a copy of `plugin/` in a temporary folder. There an alias resolves to nothing, so the code in `packages/mod/src` and `packages/contract/src` imports with relative paths only.
- `scripts/verify-install.sh` installs the plugin into a throwaway configuration and checks that the copy holds exactly the files in `plugin/`, with no TypeScript source, test or `tsconfig.json`.
- `scripts/check-directory.mjs` checks `plugin/` and the repository against the rules of Anthropic's plugin directory that can be checked here, from the README's length to the files the directory's validator can't inspect (Anthropic's plugin directory in [development.md](development.md)).

## Decisions

- **Files, not sockets.** A mod cannot keep writing to a child's input, and every session is its own process. Files need no server, survive any one of them crashing, and are easy to look at.
- **Only work that wakes a session keeps it working.** A `Stop` lists every task the engine has in flight as `background_tasks`, not only work the session waits on: memory consolidation, auto-mode scans and memory imports, teammates and cloud sessions that may sit idle, and a live connection to every artifact the session watches, which lasts as long as the session does. Taking the whole list as work kept a session that watches artifacts on LIVE after every turn, and its finished turns never aired. A task counts only when running means work that will end and wake the session: a `shell` while it works (the next decision), a `subagent`, a `workflow`, an `MCP task`, or a `monitor` that names its MCP server (an artifact's connection is a monitor with none). These are the engine's own labels, the `type` of each task. A scheduled wake-up in `session_crons` always counts.
- **A dev server never holds a session on LIVE.** Sessions keep a dev server or a watcher running while they work on a pull request, often for hours. Counting every background command as work kept such a session on LIVE through every turn, and none of its finished turns aired. A Stop tells a mod only each command's task id and the line it runs, and the line alone cannot tell `npm run dev` from `npm run build`. The processes can: the shell the engine starts for each command writes to a file named after the task, which ties each task to its processes, and `lsof` tells whether any of them listens on a port. Watchers listen on nothing, so what the line runs and what the output says catch them. Whatever cannot be told apart stays work, so a session waiting on its own timer, a test run or CI stays LIVE until it wakes.
- **One detached station.** A child of one session dies with that session; the station has to outlive whichever session started it, and decide for itself when to quit.
- **A web view for the picture.** The design system's components are the broadcast. Drawing them in the station's own web view makes the review boards and the window the same picture.
- **Motion on the compositor.** In Low Power Mode WebKit gives a page 30 frames a second and runs its timers late; the compositor keeps the display's own rate. The stinger and the ident drew their intros and outros from a timer of their own, 30 times a second, and every tick painted the glass wall, the chrome words and their blurred shadow, or the hour's rays, again. Measured on 24 October in Low Power Mode, at the window's size, the timer fired every 36 ms, about one picture in thirteen stayed up twice as long, and the GPU process worked 9 to 16% of a core against about half a percent for the board, whose CSS motion stayed smooth. Each run is now drawn from its one progress value as before, and the moving version hands the whole run to the Web Animations API as keyframes sampled from those pictures, so a storyboard frame and the moving picture match at every moment. The page draws nothing while they play, and the GPU process works 0.5 to 4%.
- **The crawl on the compositor too.** The ticker's crawl was the one motion the page still drew itself: each frame it moved the belt a little further. Anything that kept the page from its frames held the crawl back with it, while the compositor went on playing everything else, so with a game running behind the window the opens, the outros and the board stayed smooth and the crawl stepped like a slideshow. Measured on 28 October in WebKit off screen, at 480 by 270 pt, with the page kept busy 100 ms in every 120 to stand in for the game, the crawl changed its picture 13 to 16 times a second, ran at half its speed, and held one picture for up to 130 ms. Now each item, with its diamond, is a layer the compositor carries on a run of its own, from the ticker's right end to past the tab, each run starting as the one before it has carried its item's width, so the items ride end to end; the page only lays items on and takes them off, four times a second. With the page as busy, the crawl keeps its 53 px a second and moves as smoothly as when the page is idle, and through 9 s with the page frozen it never stopped. On the board, the page's process works about 2% of a core instead of 5%, and the app showing it about 0.4% instead of 3%. Two things the page used to get for free it now does itself. A crawl moved a frame at a time stood still whenever the page did; one the compositor plays runs on, so if the page is held up for more than two seconds the crawl's end comes into view before the next item is laid, and that stretch stays empty, the item coming on from the clock as on an empty belt, rather than appearing in the middle of the view. And while the window is hidden, WebKit stops the page's clock but sets its runs on again from wherever the clock has got to as it shows, as if they had run all the while; the crawl holds where it stood when the window hid and carries on from there.
- **Jingles rendered ahead of time.** Native playback needs no click, keeps to the Mac's volume and costs nothing at run time.
- **Outlines in the band.** The desktop draws a mod's `Svg` as an image, which loads no fonts and cannot read the app's theme. Outlined letters and pieces with their own ground look the same everywhere.
- **Nothing beneath is the engine's own drawing.** A mod that draws the band gets what is beneath it from `next(e)`. With no other mod there, that is the engine's own drawing, `{ type: 'engine' }`, not the empty `Box` the mod took it for, so the mod set it above the plate as another mod's line, `md` apart. The desktop draws it as an empty block, and on 24 October the gap left the plate 26 px below the band's top and 10 px above its foot. The engine's drawing now counts as nothing there, as an empty `Box` does, and the plate stands alone, 10 px from each. On the terminal, and while a survey holds the band, the mod passes it on as it came.
- **Three private switches in the station.** The window never takes the keyboard, so its app is never active, and macOS treats it that way: AppKit draws Liquid Glass flat in a window without an active appearance, and the window server ignores a pointer set by an app that is not frontmost. The station forces its panel's active appearance (`_setForceMainAppearance:`), which changes how the panel is drawn and never makes it key, and sets its window-server connection's `SetsCursorInBackground` property. The third keeps the window off Claude's full-screen Space (the next decision). All three are looked up at run time: on a macOS without one, the station logs it and carries on with flat glass, the plain pointer, or a window that can show over Claude in full screen while you switch to it.
- **Off Claude's full-screen Space.** With Claude in full screen, switching to it from another Space showed the window over Claude for about a second. The window was on every Space, Claude's full-screen one too, so the window server drew it in its corner all through the slide, and the station hid it only once macOS named Claude the app in front, which it mostly does as the switch ends. AppKit then faded it out for another quarter of a second. On 24 October, through 14 switches, the station logged `hidden` the moment macOS named Claude, and its window left the screen 259 to 289 ms later; in 13 of them macOS named Claude only as the switch ended, and the slides took about a second. macOS tells an app nothing while a switch is under way, so no hide could come soon enough. Now the window is not on that Space at all: the station finds the Spaces Claude fills alone in the window server's list of Spaces (`CGSCopyManagedDisplaySpaces`) and takes the window off them (`CGSRemoveWindowsFromSpaces`). It stays off them through every switch and every time it shows again, and a new one, from Claude going full screen again, is found within a second. While you are on one, the window stays hidden whichever app is frontmost, so an app coming forward there, Spotlight say, neither brings it up over Claude nor airs a story you cannot see. And wherever Claude comes forward, the window now hides at once, with no fade.
- **The title from the engine's own file.** A mod gets no event for a rename and no call for the title, and the hooks carry the title only when a session starts or a prompt is sent, which misses a rename between prompts. The transcript records every rename too, but it runs to megabytes. `custom-title.json` holds the title alone, so reading it once a minute while on air costs next to nothing.
- **Nothing airs from while Claude is in front.** Claude shows every story itself while it is in front. Kept for the window, those stories aired one after another when you left Claude, each looking like news that had just happened. They are dropped instead; the board and the ticker still show where each session stands.
- **Lines counted where the work happens, as it happens.** Reading only the session's own folder, as each turn started and ended, missed most of the work. A subagent in a worktree of its own works in another folder. A commit made during a turn took its lines out of the next `git diff`. A turn that ended with work still running booked nothing, and one that ran past the hour booked its lines in the next. On 23 October the report at 14:00 read +0 −0 for two sessions whose implementers had written and committed their changes in worktrees of their own. Reading a tree after every call that can change files books the lines in the hour they are written, before a commit can hide them, in whichever worktree they are written. A reading takes about 40 ms in a repository of a few hundred files, and none follows a call the engine ran read-only.
- **Git that never takes the index lock.** The mod runs git in the trees the session works in, after every call that can change files, tuned in or not, while Claude or you may be running git there too. When files were touched without changing, `git diff` writes the index back under `.git/index.lock`, and a `git commit` that needs the lock at that moment fails. `git diff-index -M` gives the same counts and never writes the index. A new untracked file counts as git will count it once it is added: its lines, or none for a binary file or one over 1 MB. Its size is looked up first, so a big file is not read at all, and it is read again only when its size or the time it last changed moves.
- **No grace for the report on the hour.** It used to join the queue at the hour with the window hidden, and air when the window next showed, up to ten minutes after the hour. On 24 October the 01:00 report aired at 01:02, the moment you left Claude, and its clock struck 01:00 two minutes late. Now it joins the queue only if the window shows as the hour strikes. A report that joined keeps its place if you switch to Claude before it airs, until the next one comes due: it was due while you were watching.
- **The usage limits from the newest reading.** Every session on air reads the same two limits, the account's, but each only when it gets a reply, so their readings drift apart between replies. Each limit on a record carries the time it was read, and the board takes the newest of each, so a quiet session's old reading never covers a busy one's. A limit past its reset is kept, as usage-band keeps it, because Claude Code stops reporting it then: dropping it would empty the meter until the next reply, where 0% is what the limit reads.
- **The settings are Claude Code's own, and `/pipcast` changes them.** A plugin declares its options in its manifest, and Claude Code stores them, shows them in a terminal's `/plugin` and in VS Code's plugin form, and hands them to the hooks module, so Pipcast keeps no preference file of its own for them: `options.json` only carries one of them on to the station, and a session's own value replaces it at every tune-in that finds it different. The desktop app this was built against (3.6556.2) shows no options for a plugin that Claude Code installed, which is how Pipcast installs, so `/pipcast <option> on` and `off` are the way to change one there. They save it with Claude Code's own command, so every place that shows plugin options sees the same value.
- **The station hears of Transparent window through the store.** It could read Claude Code's settings itself, but it would have to know where they live, which plugin id holds them, and how a `--settings` flag or a policy changes them, all of which the engine already works out for each session and hands to the mod. So the mods pass the one value on, in the store, where the station looks for everything else. A file of its own rather than a field in each record: it is one value for the one window, and `/pipcast transparency` has to reach the station from a session that is not on air.
- **Transparency is the window's own opacity.** The page cannot show what is under the window: it draws on the window's black ground. The window's `alphaValue` fades all of it at once, the window server blends it with what is beneath at no cost to the page, and `CGWindowListCopyWindowInfo` reports it, so the checks read it as the window server shows it. The 40% came from stills of the board and the desk laid over a light and a dark code editor at 35 to 65%: at 40% the headlines, the figures, the pills and the ticker still read at a glance, and so does the code beneath them, which grows harder to read through the picture from 50% up. It is a first figure, as the 70% a window can shrink to is.
- **Tuning in by itself waits for the desktop app.** The window and the band belong to the desktop app, and nothing else tells a desktop session from a headless one when it starts: both start with no surface, and a `claude -p` run from a desktop session's terminal inherits the desktop's environment. A session tunes in by itself only once the desktop app shows it, so a script's headless run never opens the window.
- **A built plugin, apart from its sources.** An install copies the plugin's folder as it is, and the mod used to run from its TypeScript sources in that folder. So every install also got the kit tests, a `tsconfig.json` that pointed at a file no install has, and the stamps the build keeps, and the line between what runs and what builds it was wherever a file happened to be put: generated files sat beside hand-written ones, and the broadcast, the scripts and the tests reached into the plugin's folder for the contract. Now the sources live in `packages/`, `plugin/` is the build's output alone, and the build checks that line every time it runs. The engine loads a hooks module written in JavaScript as readily as one in TypeScript, and the kit tests pass against the bundle, so nothing that runs changed.
- **The page says when the window is needed.** A minimized window has to come out before a segment's open and go back when the last outro ends, and only the director knows when that is: a story's desk ends early when its session moves on, the hour's review runs a page for every four sessions, and another story may be waiting. So the station never times a segment. The director answers each tick whether a segment needs the window out, and the page posts the answer whenever it changes, in the tick the director leaves the last outro: within a quarter of a second, since the page ticks every 250 ms. In the other direction, each snapshot says whether the window is out, and nothing starts until it is. Posting the answer rather than a start and an end means a page that loads again simply says no, and a station that hears `ready` takes the window back.
- **The handle is a window of its own, and the window is kept on every desktop.** The handle first rode along as a child window of the window. Soon after it shipped, on 24 October, the window server listed the window on desktop 1 alone: it was missing from every other desktop, and brought back from the tab on another desktop it came out on desktop 1, out of sight. A replay of the station's steps, attaching, detaching, hiding, showing and sliding off the edge, never pinned a window; the one thing it could not do was switch desktops while the handle was attached, which happens whenever the pointer is on the window as you switch. So the handle is attached to nothing, one level above the window, and the station moves it. Should the window or the tab still end up off the desktop you are on, the station puts it back as it shows and each time you switch: clearing `canJoinAllSpaces`, committing that with `CATransaction.flush()` and setting it again makes AppKit put a window on every Space, as the replay confirmed, and Claude's own full-screen Spaces are taken off it again right after.
- **A quarter of the window past the edge, not its centre.** Minimizing by dragging first needed the window dropped with its centre past the screen's edge, but the pointer stops at the edge, so a window held anywhere short of its middle could never get there. A quarter of the window past the edge is in reach wherever it is held but its outermost quarter, and well beyond where a move into a corner goes, which stops 20 pt short of the edge. It goes the moment the drag gets there, with the button still down, since the pointer can go no further. An edge with another display beyond it does not count, so the window still moves onto that display.
- **The listing's order within a state.** The listing sorted its sessions by state and, within a state, kept the order on air: when each session tuned in. That order once decided which four sessions were on air; once every session was, it decided nothing you could see, and each state read as if shuffled. A session stays READY until its next turn and a new session starts READY, so finished sessions gathered at the top in the order they tuned in: on 25 October the first page held four READY sessions, two of them finished eleven hours earlier, and the session at work was on the second page. Now the sessions that need you come the longest waiting first, counted as the ticker's STILL WAITING counts, so the two agree, and the rest come the newest change first.
- **The beat belongs to the desk, and the sound follows the director's events.** The beat used to be the tail of BREAKING NEWS's jingle: 36 sixteenths that came in as its last hit rang and faded about three seconds into the desk, whatever the desk did, and the hour had none. Now a step says it has the beat under it. The director tells the station as the steps change; the station mixes the beat in, loops one turn of it for as long as it is wanted, and phases it out as a step without it starts. A segment added later gets the beat by naming it on a step. Nothing in the sound is timed: a desk cut short because its session moved on takes the beat with it into the outro, and the hour's review keeps it for every page. The mixes make the joins. BREAKING NEWS's last chord holds until the desk comes in and rings on after it, and the hour's fanfare runs half a second into its desk, so the beat rises in under the jingle's ring; an outro's first chord stands about 15 dB over the beat as it goes. Charted as momentary loudness on the real files, the join into the desk keeps the beat's own level from its first downbeat on. Rising from its downbeat instead, the beat lost its first drum and left a dip of 8 dB as BREAKING NEWS's chord let go, so it rises on the last notes of its line. A turn is 43,648 frames at 48 kHz, so the beat runs at 131.96 to the minute rather than 132: at 132 exactly, Chrome's renderer, which works in blocks of 128 frames, drew each drum hit a little differently, no two turns came out the same, and a loop cut from one would not have been the beat it carries on.
- **Readable code in what ships.** Anthropic's plugin directory holds a version for a reviewer when its security scan can't read the code, or when a file that isn't an image or a font is over 256 KiB. The page used to be one minified script, React and our code together, at 225 KB; left unminified, it came to 408 KB. So React ships as its own production files, the same bytes as in its npm package, which a reviewer can compare with the package, and `station.js` holds only our code, as written, at about 150 KB.
- **Records a session left behind are deleted.** A session that stops without ending, as when Claude Code is force-quit, used to leave its record in the store for good, with its title, its questions and Claude's last words. The station showed it no more once its check-ins stopped, but nothing deleted it, and Anthropic's plugin directory asks how long a plugin keeps what it collects. Now every session that tunes in first deletes the records no session has written for an hour. Waiting an hour, rather than the 45 s after which the station stops showing a record, keeps a Mac's short sleeps from costing a running session its record; one that slept longer writes its record again at its first heartbeat after the Mac wakes.
- **Segments on cue, in a build that ships nowhere.** Trying a change to the report on the hour meant waiting up to an hour for it, and one to BREAKING NEWS waiting for a turn to end. A way in for a cue in the station that ships would have been there in every install, for anything on the Mac to use, and Anthropic's plugin directory scans a plugin for anything it does that its README doesn't say. A flag that turns it on is still a way in. So the cues are compiled into a development build alone, and the live checkout always runs as that build: `scripts/live.sh`, the one way a change reaches the app, builds it, so there is no second switch to keep in step with the first. Its way in is a file, as everything between Pipcast's programs is: a cue sits in the store, which only you can write to and where a program of yours could already write a session's record. And a cue airs on a director of its own rather than on a director that knows about cues, so what airs is what a session would make air, and the director that ships is the one that was tried.
